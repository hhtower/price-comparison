# 标准商品维护

标准目录定义可以比较的商品身份。商家报价说明该商品以什么条件交付；标准化负责依据当前报价证据匹配目录，导购负责在用户条件内选择报价。

## 身份与报价

- 先确定平台或发行主体、交付对象，再确定正式套餐档位或具名工具。账号、订阅权益、额度、资格、代操作服务、软件许可和教程不能仅因涉及同一平台而互相替代。
- 地区、期限、数量、渠道、凭据格式、交付方式和售后通常属于报价条件。只有这些差异对应独立产品、正式计划或不同授权对象时，才作为标准身份的区别。
- 资格或申请操作不等于权益已经开通；验证码接收不等于完整账号控制权；工具许可不等于卖方替用户完成操作。
- 教程按直接教学的产品或操作对象区分；科研、编程、安装和排障是教学主题，不据此拆分同一对象。ChatGPT 与 Codex 的操作教程分别维护，跨产品课程保留组成。
- 保留已确认的历史标准及其适用条件。缺货、报价稀少或暂未匹配，不能单独作为删除、合并或撤销准入的依据。

## 定义与相邻边界

每条定义应能独立说明交付什么、适用什么对象，以及与容易混淆的相邻标准如何区分。判断所需的信息不能只存在于另一条标准的排除说明中，也不能依赖未附在目录中的“原文”“原店”或审核过程。

上位类与专类同时保留时，应明确归属边界。相邻标准的包含、排除范围必须一致；不能在引用其他标准时擅自缩窄或扩张它的范围。通用定义不记录某一报价的审核结论，不将商家承诺升级为整个标准的保证。

发现歧义时，先核对已有定义及分类约定。保留已确认的标准范围，具体报价无法证明交付对象时按未匹配处理，不为了让某条报价匹配而改写整个标准。

## 名称与召回

名称、已确认别名和规范身份用于检索。别名表达同一身份的称呼，不是包含关系；不能把排除条款、用途说明、商家标题或历史归属直接当作别名。

空格、大小写和全半角可以归一；`Pro` 与 `Pro+`、不同数字档位和倍率不能因此合并。跨标准重复的别名需要消歧。标准化和导购使用相同的身份名称构造与文本规范化，各自保留候选预算和购买条件检查。

召回只是提供可判断的候选。规则推测的身份不应被大量词面结果挤出候选集合，也不能压过明确商品证据而直接决定归属。候选进入模型后，仍须通过定义、当前证据与响应校验。

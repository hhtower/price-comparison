# PostgreSQL 运行配置

使用 PostgreSQL 16 或更高版本，通过 `DATABASE_URL` 配置连接。生产环境应限制网络访问，妥善保存连接凭据。

## 连接容量

每个 API 和 worker 进程分别使用连接池。配置 `PG_POOL_MAX` 时，将所有实例纳入数据库连接预算，并为迁移、管理和监控预留连接。

连接超时、语句超时及可选 schema 的配置见 [数据库连接配置](../../apps/api/src/database/database.providers.ts)。使用连接池代理时，应先在测试环境验证迁移、API 和后台任务。

## 监控

关注连接数、慢查询、锁等待、磁盘空间和备份状态。可使用 `pg_stat_activity` 查看当前活动与等待情况，按需启用 `pg_stat_statements` 汇总查询开销。性能评估入口见 [性能说明](../performance.md)。

采集诊断信息时删除连接凭据、查询参数中的敏感数据及个人信息。

API 的原生 PostgreSQL 和 Kysely 查询共用慢查询与失败日志。日志保留请求路径、错误码及不含 SQL 原文的查询指纹；指纹仅在同一进程生命周期内稳定。记录的查询耗时不包含连接池获取等待，排查请求延迟时需同时查看连接池和请求日志。

## 初始化与备份

初始化和升级统一运行 `npm run db:migrate`，无需逐个执行迁移文件。升级前备份数据库、停止相关服务；迁移完成后启动同一版本的 API 和 worker。具体流程见 [开发与部署](../../WORKFLOW.md)。

统计优化迁移会创建 AI 与价格历史查询索引，并回填抓取计数及轻量任务查询记录，耗时和所需磁盘空间取决于已有数据量。查询记录与源数据在同一事务中更新，不使用延迟缓存。蓝绿发布应先确认旧 API 与迁移后结构兼容，由旧槽继续承流，暂停相关写入 worker 后执行迁移；迁移完成、新槽探活通过后再切流并恢复 worker。

结算状态统一使用结构化字段，展示层不解析支付文案或旧报表。上线前须完成报价、目录投影、历史价和任务报表的数据迁移；即使已执行结算状态迁移，也要继续执行后续迁移至最新版本。迁移期间保持爬虫和结算补采 worker 停止，验证迁移成功后再恢复服务。

已有数据升级到完整结算结构时，在本地配置目标数据库的 `DATABASE_URL` 和 `PG_SCHEMA`，停止写入后依次执行：

```sh
npm run db:migrate -- --to 058_settlement_data_contract_20261124
npm run db:prepare-settlements
npm run db:prepare-settlements -- --apply
npm run db:migrate
```

修复程序要求明确指定 `PG_SCHEMA`，目标不存在或缺表时直接失败，不回退到 `public`。默认只预览；`--apply` 在 `.local/settlement-preparation/` 保存精确保留金额和时间精度的备份后原子写入。只有已有明确数量或同一报价的多件历史证据才用于还原总额；旧历史曾默认填入数量 `1`，不能据此认定单件。缺乏可信数量或无法还原合法总额的报价清除核验结果并安排重采，相关历史记录降为预估，原商品标价保留。程序不访问商家或调用模型。

`059` 只安装严格约束和新结构函数，遇到未处理的旧报价会失败，不会在服务启动时修复或猜测数据。新库直接迁移到最新即可；已完成升级的数据库无需再次执行上述定向迁移。

使用定期 `pg_dump` 或托管数据库备份，并在隔离实例上演练恢复。迁移失败时先检查原因及数据库状态，不要在业务库中手工删除迁移记录或反复执行不明脚本。
